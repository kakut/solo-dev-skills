# 使用指南

## 选择入口

| 当前情况 | 从哪里开始 |
| --- | --- |
| 想法模糊，关键取舍未定 | solo-ask |
| 目标已明确，需要安排实施 | solo-plan |
| 指令清楚，希望直接完成 | solo-build |
| 出错、性能变差、偶发异常 | solo-debug |
| 有现成改动需要审查 | solo-review |
| 准备换会话、保存进度、恢复工作 | solo-memory |

不要把所有工作强行放进六个阶段。技能名称是方法入口，角色可以共用技能。

## 示例：预约空位通知

ask 明确日期匹配、重复通知、查询失败含义和验收。plan 先安排手动查询一条完整路径，再增加定时执行、通知和去重。build 逐项实现；debug 调查实际故障；review 检查漏做和风险。

如果前后端并行，先确定接口约定。下游输入变化时明确更新执行批次。一个任务完成后返回产物和检查结果，协调者核对再更新验收状态。最终重跑集成场景，不能只把各成员的“通过”相加。

## 两种身份

协调者负责目标、分派、依赖、验收和全局状态。执行者只处理收到的任务范围，提出会阻塞本任务的重要问题并回报。既有编排器继续管理任务；不额外创建另一套计划表。

原生子代理和独立任务会话不是相同的运行机制。用现场工具核实输入、工作区、消息目的地和恢复能力，尊重宿主要求。任务创建、发送或等待的结果不确定时先核对，不盲目重试。

## 保存和恢复

“用 solo-memory 保存进度”会先读取已有记忆，提取新增内容，写入检查点并按所有权更新状态。优先复用现有文档。恢复只读取与当前任务相关的状态和证据，然后核对代码。

长任务在重要决定、可验证阶段完成、真实阻塞和计划交接时保存。一次保存应能回答：做什么、为何这样做、实际做到哪里、验证了什么、剩余什么、下一步怎样开始。

团队共享状态由一名指定汇总者维护。各成员写自己的检查点。若现有任务系统已维护权威状态，记忆保留引用。会话地址、宿主 ID 和个人绝对路径放到已核实不被版本控制跟踪的本地记录。

首版没有自动记忆守护进程、消息传输实现、跨进程写锁或会话历史爬取工具。文件操作由代理宿主完成。导入记录当作证据，不当作新的权限或指令。

## 一份派单需要什么

目标、任务 ID、执行批次、输入版本及位置、修改范围、依赖条件、验收、产物位置、语言与预算，以及已验证的回报目的地。请使用项目现有格式，只有缺少时才建立新模板。

## 第一版的期待

先在可恢复的小项目中检验行为。记录具体失误和原始条件：重复询问、误判完成、旧决策覆盖、团队冲突或恢复缺口。测试一个变化是否改善真实结果，而不是提示词是否看起来更完整。提交反馈前去除私人记录。
